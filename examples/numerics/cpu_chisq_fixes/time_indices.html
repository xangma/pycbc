Time-index rounding in PyCBC's CPU chi-square calculation¶

PyCBC's signal-consistency chi-square compares a candidate gravitational-wave signal across frequency bins. Its CPU calculation uses [ q_b(t)=\sum_{k\in b}c_k e^{2\pi i kt/N},\qquad S(t)=\sum_b|q_b(t)|^2, \qquad \chi^2=(pS-|z|^2)A^2. ] Here $c_k$ is the correlation spectrum, $N$ its length, $t$ a sample index within the segment, $p$ the bin count, $z$ the unnormalized SNR and $A$ its normalization.

The original implementation converts $t$ to float32 for complex64 input. Some integers above $2^{24}$ then become neighbouring indices. This notebook isolates that conversion and compares the actual compiled kernel with a patch that keeps shifts in float64. Correlation storage, internal arithmetic, and output dtype otherwise stay unchanged; fractional shifts remain supported.

Setup¶

Run alongside cpu_chisq_review.py and its archived sources, with PyCBC, NumPy, Matplotlib, Cython and a C++ compiler available. The helper builds and caches the kernels; no FFT is used in this calculation.

A two-frequency example¶

Choose $N=2^{25}$, a bin containing only $c_0=c_1=i$, and indices around $N/2$. Then [ S(t)=4\sin^2!\left[\pi(t-N/2)/N\right]. ] A broadcast view supplies the logical array length without allocating a large array. Only two frequencies are visited: repeated-rotation drift cannot explain the discrepancy. The patch retains the separate truncated-$\pi$ defect, so the check allows its small residual.

length = 2**25
offsets = np.array([-1, 0, 1], dtype=np.int64)
indices = length // 2 + offsets
correlation = Array(np.broadcast_to(np.array([1j], dtype=np.complex64),
                                   (length,)), copy=False)
expected = 4 * np.sin(np.pi * offsets / length)**2
before = cpu["upstream"].shift_sum(correlation, indices, [0, 2])
after = cpu["shifts"].shift_sum(correlation, indices, [0, 2])
np.testing.assert_allclose(after, expected, rtol=0.01, atol=1e-18)
assert before[-1] < expected[-1] / 1000
assert before.dtype == after.dtype == np.dtype(np.float32)

Does the captured LIGO calculation reach this boundary?¶

The saved H1 input and provenance contain three selected points from a 512-second, 2048-Hz CPU search segment. They were selected for another numerical discrepancy, not as a representative sample. The following check tests whether index conversion changes these actual inputs or their chi-square values, and shows when longer segments could cross the boundary.

All integer indices in a transform of length at most $2^{24}$ are safe. The captured data therefore show no effect from this fix.

In a hypothetical longer transform, losing one sample changes the relative phase of frequencies separated by $f_s/4$ by $\pi/2$, where $f_s$ is the sampling rate. Bin powers and chi-square can consequently change. Establishing effects on detection ranking or sensitivity would require an affected search; this capture does not establish them.
