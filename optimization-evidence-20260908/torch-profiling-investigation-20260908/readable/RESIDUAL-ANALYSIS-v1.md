# Remaining CPU gap and GPU setup opportunities

The updated Torch CPU executable takes **104.400 s**, versus **66.933 s** for the updated standard backend: a **37.467 s difference between medians**. Both use the qualified loader change, 384 templates, five segments, 1,904 valid detector seconds, CPU core 8 and one numerical thread. Three fresh unprofiled runs were measured per route on the shared host.

The run boundaries put the CPU difference in filtering. Same-repeat full-wall differences are 36.999, 37.279 and 37.771 s; filtering differences are 37.304, 37.503 and 37.995 s. Torch CPU setup is slightly shorter in all three pairs. These paired statistics differ from differences of independent medians.

The existing qualified 2M IFFT microbenchmark takes 33.520 ms per current promoted in-place plan execution, versus 16.034 ms for the standard single-precision reference. Multiplying the difference by the workload's 1,920 IFFTs gives **33.574 s**, equivalent arithmetically to 89.61% of the current wall gap. This compares separate experiments and is only evidence for prioritization. It is not a causal decomposition, an unavoidable precision penalty, or a prediction of recoverable time. The whole promoted path includes two conversions. The standard single-precision reference also fails the stricter fixed 36-case matrix that the accepted Torch route passes.

The older out-of-place Torch profile records 8.699 s in the plan's 3,840 tensor copies and about 0.148 s between the public IFFT wrapper and the native-plan call boundary. The copy total cannot be transferred to the current in-place implementation, but it makes conversion measurement a stronger lead than further wrapper cleanup. The next frozen diagnostic measures promotion, native DFTI, version/status bookkeeping, demotion and whole executions of the current plan, with paired timing controls and unchanged precision checks before and after. A cached NumPy-view conversion is a candidate only if that evidence supports it.

For CUDA, current full-wall median is **21.766 s**. Per-run decomposition gives medians of 10.232 s setup, 4.574 s outside the internal timer and 6.969 s filtering; median setup-plus-outside is 14.805 s and median overhead fraction is **68.02%**. Independent medians need not add exactly. The outside-internal interval must not be relabeled entirely as import time.

The historical CUDA profile has **1,003 MKL descriptor creations / 2.558 s cumulative**: 1,001 forward calls account for 1.533 s and two inverse calls for 1.025 s. Although Welch calls FFT 999 times, its entire FFT subtree totals only **0.657 s**. The aggregate 2.558 s therefore cannot be assigned to Welch or claimed as descriptor-reuse savings. Other ancestors include full-length whitening transforms and inverse-spectrum truncation. The relevant MKL, PSD, strain and time/frequency-series source files are byte-unchanged between that profile revision and the current source; current costs still need measurement.

The next GPU setup diagnostic should record descriptor keys, caller, chronological order, creation time and execution time on the current source. Separate first-use from repeated-key construction before choosing a plan-reuse scope. Only repeated, material construction cost supports a reuse change; cold initialization and distinct descriptor sizes may explain much of the total. Fresh whole-process measurements and the existing strain, PSD and trigger gates remain necessary for any candidate. Startup attribution is the following priority if descriptor reuse offers little gain.
