# Final same-workload profile interpretation

The final qualified Torch CPU execution is slower principally in compressed-waveform decompression and the large search inverse FFTs. Three unprofiled repetitions give median full-process times of **32.313625 s for normal CPU, 80.628090 s for Torch CPU, and 20.335830 s for Torch CUDA**. These timings, and the separate profiles below, use source `837f38d493420043e45fb1ad210a0ccf68bacbaa`, the same 96-template compressed bank, 1,904 unique valid detector seconds, and 512-second segments at 4,096 Hz. Each template is filtered against five segments: 480 inverse FFTs of 2,097,152 complex samples. The host is `len`, a Threadripper PRO 3995WX, with affinity `[8]` and one-thread settings; CUDA additionally uses one RTX 4090. The normalized executable arguments, shared input hashes, profile environments, extracted function/caller measurements, source hashes, and evidence hashes are in [profile-interpretation-v5.json](profile-interpretation-v5.json). All numbers here concern this final workload.

The table uses **inclusive cProfile time for each named path**, in seconds. The first two paths are disjoint: waveform decompression does not call the search IFFT. Their children must not be added again. CUDA host call times are omitted from this CPU attribution table because asynchronous launch timing is not device execution time.

The first two differences total **45.943802 s**, or **94.99%** of the **48.366999 s** difference between cProfile self-time totals (34.485359 versus 82.852357 s). This locates the gap in this profiled pair; it does not assign 94.99% of the unprofiled timing difference or predict the speedup of an unimplemented change. Full-process cProfile runs took 35.527097 and 83.954785 s. Each profiler has only one execution per scheme, and its overhead is separate from the three-repeat unprofiled measurements.

Torch decompression uses the generic tensor implementation in `pycbc/waveform/decompress_torch.py:74–152`, even for degree-one interpolation. It constructs dense output indices and stencils, locates intervals with `searchsorted`, computes Lagrange weights, gathers amplitude and phase, performs two reductions, and forms the complex waveform. CPU and CUDA interpolation arithmetic is promoted to double precision to match the established backend's arithmetic and interval boundaries. Normal CPU instead calls the compiled interpolation routine through `pycbc/waveform/decompress_cpu.py:34–54`. This is a concrete implementation difference consistent with the measured cost. In the Torch CPU caller records, **192 reductions called specifically by `_inline_interp` consume 6.430300 s**, and `_lagrange_weights` consumes **5.224622 s inclusive**. Those are already inside the 26.624610 s decompression time. Of the 7.983136 s aggregate Tensor `sum` self time, another 1.552714 s belongs to `squared_norm`; assigning all reductions to decompression would be incorrect. Native sampling independently shows double-precision Torch row reductions, tensor indexing and `searchsorted` among its leading symbols. The profile establishes expensive eager tensor work; it does not measure memory-bandwidth saturation or isolate allocation cost.

The large Torch CPU IFFT takes the conservative **complex128 FFTW workspace route**. At this source revision, direct MKL is allowed only at 32,768 samples and direct FFTW inverse plans only at the explicitly listed sizes up through 131,072; the selected 2,097,152-sample transform is outside those sets (`pycbc/fft/torchfft.py:39–81,960–987`). The profile records 480 calls to `_FFTWCPUWorkPlan.execute` at line 350, where input is copied into a retained complex128 tensor, transformed in place, and copied back. This inner call takes **26.796339 s inclusive**: **24.591437 s self time** at the wrapper containing the native FFTW call and **2.202509 s in 960 Tensor `copy_` calls** directly attributed to that wrapper, with a small remaining child overhead. The native call is not exposed as a separate cProfile function, so the wrapper self time is not Python bytecode time. Normal CPU calls the bound MKL inverse transform at `pycbc/fft/mkl.py:189` for **7.103488 s**; its native profile shows single-precision inverse-FFT symbols. Visible double-precision FFTW shared-library rows sum to **26.93% of Torch CPU sampled user-cycle event periods**. Some FFTW symbols are unresolved addresses, so this supports library ownership without identifying every FFT stage. Precision, FFT library, planning, memory layout and the conversion passes change together; these observations do not isolate their individual contributions.

Thresholding and point chi-square are secondary contributors to the CPU gap. Source inspection shows the eligible Torch CPU routes reuse the established native CPU kernels through shared NumPy/Torch storage (`pycbc/events/threshold_torch.py:946–1031` and `pycbc/vetoes/chisq_torch.py:650–718`), matching the native symbols observed. The fused point-chi-square entry itself takes 1.910586 s on normal CPU and 1.920440 s on Torch CPU. There is no basis here for attributing tens of seconds to thresholding or chi-square dispatch.

For the normal CPU reference, the report's **FFT ownership group is 12.079184 s, or 35.03% of cProfile self time**. It includes both reusable search transforms and other FFT work, including 4.177161 s self time in MKL descriptor creation. It is not a claim that search IFFTs alone occupy 35.03% of full-process wall time. The large **remaining** ownership category is also not unexplained Python overhead: native `lalframe.FrStream*` calls alone account for **6.669477 s** in the CPU profile, **6.683462 s** on Torch CPU and **6.689354 s** on CUDA. Torch's generic Tensor operations fall there when their operation names do not uniquely identify a pipeline stage. Likewise, the CPU correlation group's zero reflects the classifier's ownership rules; native `perf` still reports the compiled correlator at 1.98% of user-cycle event periods. The full raw call graph and caller edges are more informative than forcing those generic functions into guessed stages.

CUDA moves the template work out of the dominant CPU paths, leaving a substantial host setup cost. Its cProfile internal executable timer records 16.396775 s total and 13.576284 s setup (82.80%); these exclude early imports and final event-file writing and remain profiled measurements. Its largest host self entries include MKL descriptor creation at 2.531860 s and the frame calls above. In the separate Torch operator trace, `_triton_pointwise_chisq_bin_kernel` is the largest recorded device event at **0.291365 s across 149 launches**, **62.15%** of **0.468803 s** summed CUDA device-event time. Host launch and stream-synchronization entries take 0.299936 and 0.261818 s respectively in that trace. Device-event totals are neither end-to-end wall time nor a GPU-utilization measurement, and they must not be added to overlapping host operator totals. The profiler was initialized before executable entry; its event table does not cover arbitrary non-Torch host work. The trace and native CPU profile together support host setup as a major remaining end-to-end cost while locating the largest measured device kernel.

This interpretation reads the final archived cProfile files, native exports, Torch key averages, receipts and final report. The relevant source files were checked byte-for-byte against the recorded commit. No new workload, optimization or source change was performed. Native percentages retain `perf`'s direct `cycles:u` event-period denominator; visible rows omit small symbols and are not renormalized. Earlier component benchmarks are not used to explain this workload.
