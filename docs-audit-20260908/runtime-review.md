## Follow-up: offline environment gate requires wording correction

Reviewed the parent's subsequent `docs/torch_search.rst` paragraph as requested, changing only this report. Its claim that `PYCBC_TORCH_CUDA_GRAPH=1` requests only existing captures and cannot itself capture is contradicted by the source call chain:

- `bin/pycbc_inspiral:265` calls `matched_filter_and_cluster`, assigned to `full_matched_filter_and_cluster_symm` for the symmetric path in `pycbc/filter/matchedfilter.py:243–248`.
- `pycbc/filter/matchedfilter.py:350–361` uses the environment flag to enter `replay_symmetric_cuda_graph`; `matchedfilter_torch.py:109–113` delegates to the graph helper.
- `pycbc/filter/_torch_cuda_graph.py:337–340` calls `capture_symmetric_cuda_graph` before replay. That capture function accepts an empty capture dictionary (`:284`) and creates/stores a new graph for eligible bindings (`:297–334`). No explicit capture call in the executable is required.

Suggested replacement: “Set `PYCBC_TORCH_CUDA_GRAPH=1` to request graph filtering. On the first eligible symmetric-filter call, the replay helper attempts capture; subsequent calls with matching bindings replay the graph. Alternatively, call `control.capture_cuda_graph_symm(segnum, window, template_norm)` explicitly; successful capture enables replay.” Keep the existing eligibility, eager-fallback and error qualifications. This establishes the supported control flow, not a speedup claim or whole-executable capture. The page remains untouched by this follow-up, and no runtime suite was rerun.
